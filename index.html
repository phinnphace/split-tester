The problem

When a diagnostic gets reported as a finding

Machine learning practitioners regularly report internal validation as if it were an empirical result. It isn't. It's a measurement of how the model performs on one particular slice of one particular dataset on one particular day — shaped by configuration choices that were never made explicit.

The specific slice is determined by the train/val split. The specific configuration includes the split ratio — what fraction of the data is reserved for "validation". That ratio is almost always 80/20, not because it was derived experimentally on your data, by you, not because it was validated against alternatives, but because it was in the textbook, which inherited it from the previous textbook/journal, which inherited it from practices that coalesced before the cost of computation allowed better.

The number you report depends on where you drew a line. Arbitrary? Arguably. If you didn't test where you drew it, you don't know what you reported.

This is not a fringe case. It is the default condition. Internal validation — the number that shows up in papers, blog posts, model cards, and production dashboards — is at best a calibration diagnostic. It tells you the data behaved that day. It tells you the cat didn't spill coffee on the GPU. It does not tell you how the model generalizes, because generalization requires external validation that most workflows never reach.

Historical context

How 80/20 became the default nobody questions

The 80/20 split did not emerge from the domain of ML.

Tracing exactly when and how this specific ratio became entrenched — across textbooks, benchmark datasets, standard library defaults, and reproducibility norms — is ongoing research. What is already clear is that the ratio took hold instead of the methodology that should have accompanied it. The how and why in the original literature. They did not travel well.

Internal Validation (The 80/20 Split): You build the model on a dataset and test it on a held-out portion of that exact same dataset. This only proves that the model functions on data collected under the exact same parameters, temporal conditions, and systemic biases.

External Validation: You take the finalized model and apply it to a completely independent cohort—patients from a different hospital network, or environmental surveillance data from a different state or decade. This demonstrates the model actually learned the underlying phenomenon, not just the artifacts of the local dataset.

By adopting the 80/20 split from early business intelligence, the ML community effectively truncated the scientific method. They took an internal validation tool and began treating it as if it satisfied the requirement for external validation.

It predates modern neural networks, large-scale datasets, and most of the domains where it is now applied without modification. Ironically, one of the earliest uses I attribute the start of this methodological choice comes from Larson in 1931. The irony comes from who he is in medicine and science.

Ever take “RCR” (responsible conduct of research) or any methodology course? How about the very existence of clinical standards and not just vibing medicine? Well we have that guy to thank for not having phrenology and the evil eye be the basis of modern medicine.

He was like, ”...guys, I think we need to do things with some standards and logic. By logic I mean causation. If someone is sick we use diagnostics to assess (rule in, rule out) and then treat them based on findings. Treat them with what? Medicines and therapeutic practices that are tested and demonstrated effective to heal/mitigate their illness. “ This was novel stuff less than a hundred years ago.

The "Benchmark, Publish, Repeat" Cycle — This conflation is the engine of the ML publication machine. Benchmarks are not results. Lets sing it together! When researchers use a standardized corpus (like the Penn Treebank in the Brill and Wu paper) the 20% test set is treated as the ultimate proving ground.Because the 20% holdout comes from the exact same distribution as the 80% training data, it is essentially a closed loop. The algorithm is never tested against the chaotic, shifting reality of the real world.

Validation set trivially small. A model achieves "State-of-the-Art" (SOTA) status, gets published, and is treated as a solved problem. But when that same model is deployed in a high-stakes pipeline—say, processing clinical diagnostic data or evaluating vulnerability indices across new geographic census tracts—it collapses. It was never externally validated; it was just highly optimized for a specific, isolated matrix.

When a marketing team predicts direct-mail response rates, a closed-loop 80/20 internal validation is fine. If the model decays when applied externally to a new demographic next year, the worst outcome is a slight dip in ROI.

80/20 was convenient. It fits on a page. It became a working example. Worked examples become defaults. Defaults become invisible.

A demonstration

One model. One dataset. Five ratios. What if you use another split ratio? I am only sharing one example, because the example is not the "thing" that matters. I hope that much is clear.

The domain is incidental. What follows used handwritten Chinese characters from the CASIA-HWDB database — 40 images, a Random Forest classifier, and a fixed seed. The characters could have been anything. The result would have been structurally identical.

These are five correct answers to the same question. The question was never "what is this model's accuracy" — it was "what is this model's accuracy given a specific split configuration that was never made explicit." Stopping at 60/40 gives 60.2%. Stopping at 90/10 gives 81.6%. Neither number is wrong. Both are incomplete.

Notice also that 60/40 performs worse than 50/50. More training data did not help — it shrank the validation set to the point where a few samples determine the entire reported number. The relationship is not monotonic. The assumption that "more training data → better validation performance" is not safe to hold without testing it.

The conventional 80/20 sits at 73.5% — more than 8 points above the worst possible answer, 8 points below the best. It is not wrong. It is not optimal. It is one configuration out of several, reported as if configuration didn't exist.

The tool

delta_split.py

A single function. Drop it on any model, call it once, and it tells you how much the split ratio alone is moving your internal validation number. Same model, same seed, same data — only the cut point moves. The spread it returns is the calibration signal: how sensitive your reported number is to a choice you probably didn't make explicitly.

Only dependency is numpy. Anything with sklearn-style .fit() / .predict() works without configuration:

from delta_split import delta_split
from sklearn.ensemble import RandomForestClassifier

d = delta_split(RandomForestClassifier(), X, y)
# train_50_val_50: train=150, val=150, internal-val=0.555
# train_60_val_40: train=180, val=120, internal-val=0.648
# train_70_val_30: train=210, val=90,  internal-val=0.673
# train_80_val_20: train=240, val=60,  internal-val=0.735
# train_90_val_10: train=270, val=30,  internal-val=0.816
# delta (spread): 0.261  [high=0.816, low=0.555]

d.spread   # 0.261  ← how far the split ratio can move your number
d.range    # (0.555, 0.816)
d.high     # 'train_90_val_10'  (highest internal-val — NOT "best split")
d.low      # 'train_50_val_50'
dict(d)    # JSON-serializable

What it is and isn't

It is a calibration check, not a result generator. What it returns are preliminary diagnostics — not findings, not benchmarks, not an optimal split. The point is to put a number on something that was previously invisible: how much a single unreported configuration choice is moving the number you're about to report.

It deliberately does not pick a winner. Optimality is contextual. Small datasets behave differently from large ones. Class imbalance interacts with split size. The tool surfaces the sensitivity; the interpretation is yours.

Hooks for non-sklearn stacks

HookWhat it acceptsDefault
metriccallable(y_true, y_pred) → floataccuracy

model_factorycallable() → a fresh modelclone model

Keras — adapt predict for probabilities, pass a factory so each split gets fresh weights:

d = delta_split(
    model_factory=build_model,
    X=X, y=y,
    fit=lambda m, xt, yt: m.fit(xt, yt, epochs=20, verbose=0),
    predict=lambda m, xv: np.argmax(m.predict(xv, verbose=0), axis=1),
)

PyTorch — wrap your loop in the hooks:

def train(model, X_tr, y_tr):
    # your loop; return model or mutate in place
    return model

def infer(model, X_val):
    model.eval()
    with torch.no_grad():
        return model(to_tensor(X_val)).argmax(1).cpu().numpy()

d = delta_split(model_factory=build_net, X=X, y=y, fit=train, predict=infer)
Why one fixed shuffle? Every split reuses a single shuffle drawn from seed. Only the cut point moves. The spread you see is attributable to the ratio alone — not to a different random draw. The ratio is the only thing that changed.
